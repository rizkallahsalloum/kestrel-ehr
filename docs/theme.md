# Kestrel theme

Phase 1 of the frontend plan, approved with the exceptions below. The design system is a learning prototype; nothing here is a claim of accessibility compliance beyond the measured contrast ratios listed.

## Pipeline

1. `design-reference/design-tokens.tokens.json` is the Figma export and the source of truth. Treat it as read-only; replace it with a fresh export.
2. `pnpm tokens:build` (`scripts/build-tokens.mjs`) resolves every `semantic.*` token through the primitives and writes `--k-semantic-*` variables to `src/styles/tokens.css`. Do not edit that file by hand.
3. `src/app/globals.css` maps those variables to Tailwind names in `@theme inline static`. Every mapping has a literal fallback equal to the current Figma value.
4. The `:root` block at the top of `globals.css` holds the `--kf-*` overrides. It is the only place where a value differs from, or is missing in, Figma.

Review everything at `/dev/theme` (development only: `pnpm dev`, then open the route).

## Approved overrides

All overrides live in the `:root` block of `globals.css`. Components use the Tailwind names, never the `--kf-*` variables or raw hex values.

### Intended usage of the warning colors

- `warning` text on `warning-subtle` fill, outlined with `warning-line`: advisory demo alerts, advisory summaries, the synthetic-data banner.
- Form errors are amber, never red. Red is reserved as described in "Severity colours" below.
  - Field stroke and focus glow: `warning-stroke` (`warning.border-strong`, #9C6A15). It is a non-text indicator and only needs 3:1.
  - Error message text and icon: `warning` (#8A5A0E). `warning-stroke` is not used for text, because it falls below 4.5:1 on `page` and on `warning-subtle`, where the acknowledgement form sits inside advisory alerts.
- `status-warning`: status dots and other non-text indicators. Always pair a dot with a text label.

### Severity colours (Phase 8c; replaces the Phase 5 "Red and orange" rule)

One rule, shared with `.cursor/rules/kestrel.mdc`:

- **Red** (`danger`, `danger-ink`, `danger-subtle`, `danger-line`, `status-critical`) marks **severe and critical** states: blocking demo alerts, severe allergies, critical status dots in Today's queue, and the offline sync state. It also stays on the destructive "Cancel draft" confirm button (`Button variant="danger"`).
- **Orange** (`warning`, `warning-subtle`, `warning-line`, `status-warning`) marks **moderate and warning** states: advisory demo alerts, mild and moderate allergies, and warning dots. Form errors and the synthetic-data banner stay orange (`warning-stroke` for field strokes).
- **Green** (`ok`, `status-stable`) marks stable states: "No alerts" queue dots, the connected sync dot, the Privacy button's "Privacy on" state, clear states. (The decorative queue chip avatars also use a green, teal and blue palette with no meaning; see Phase 8d.)
- **Solid versus subtle.** The strongest red treatment is for the critical allergy-conflict banner and critical states: `danger-subtle` fill, a 2px `danger` border and a ringed red icon. Pills, dots, tags and flags use the subtle or outlined error style: `danger-subtle` fill with an inset `danger` ring (badge, allergy pill), `danger` text and outline on white (severity tag), or a red dot with an outline ring. Nothing in the app uses a solid red fill except the "Cancel draft" button.
- **One icon.** Every alert uses the triangle (`AlertTriangleIcon`). The circle variant was removed from the repository (`AlertCircleIcon`, `severityIcons`); a browser test fails if it comes back. Status dots stay dots.
- **Blocking versus advisory is never told apart by colour alone.** All maps are in `src/components/ui/severity.ts` (`severityOutline`, `severityFill`, `severityText`, `severityIconText`, `severityDivider`):

  | Cue | Blocking or severe (`critical` tone) | Advisory, mild or moderate (`warning` tone) |
  | --- | --- | --- |
  | Colour family | red (`danger*`) | orange (`warning*`) |
  | Border width | `--border-width-emphasis` (2px) in `danger` | hairline (1px) in `warning-line` |
  | Label text | "Blocking", "Severe", "N blocking alert(s)", "Severe allergy", "Critical alert" | "Advisory", "Moderate", "Mild", "to acknowledge", "Warning" |
  | Ordering | first | after blocking; acknowledged advisories last |

  Where a 2px border would change an element's size, the emphasis is drawn without it: the `Badge` uses an inset ring, `SeverityTag` trades one pixel of padding, and the review count pill always reserves a 2px border (transparent unless blocking).
- A summary takes the **treatment** of the highest severity it summarizes: the allergies card (outline colour, icon and dividers; since Phase 8d its outline is a hairline in every tone, because it is a summary, not a blocking alert), the patient hero allergy pill, the E-Rx allergy tile, the medication safety summary, the review count pill and the chart alert banner use the red treatment when anything blocking or severe is present.
- **Test hook.** Every severity surface carries `data-severity="critical" | "warning"`. `severityColourViolations` in `tests/browser/support.ts` fails a page if a red colour appears outside a `[data-severity=critical]` element or an orange one inside it.
- Ordering is enforced in the components, not only by the database queries: `bySeverity` (allergies) and `orderAlerts` (prescription alerts) are unit-tested, and the chart banners are sorted blocking first.

### Usage rules from the contrast report

- Do not put `ink-muted` on `surface-warm` (4.45:1). Use `ink-secondary` (4.65:1) or `ink-strong` on warm fills.
- `ink-muted` is fine on `surface` (5.24:1) and `page` (4.77:1).
- Field placeholders and suffixes use `ink-placeholder` on `surface`, and `ink-secondary` on the warm read-only or disabled fill (`ink-placeholder` on `surface-warm` is 4.45:1).
- Disabled controls are exempt from contrast minimums but keep their visible label.

### Changes from the Phase 5 review

- **Red is no longer used for detection** (superseded in Phase 8c, see "Severity colours"). Converted from red to the orange blocking treatment: the chart alert banner, the chart allergy panel, the patient hero allergy badge, the E-Rx severe-allergy tile, the E-Rx medication safety summary, the review count pill and the E-Rx blocking alert card. The `critical` tones of `Badge`, `SeverityTag`, `StatusDot` (orange dot with an emphasis outline ring), `Card`, `PanelTitle` and `AlertBanner` changed with them.

- **Section tracker uses a container query** on the tracker itself. Below `@tracker-row` (20rem) the steps stack with full labels. From `@tracker-row` they sit in one row with short labels ("Directions" for "Directions and supply"). From `@tracker-full` (28rem) the full labels return. - **Disabled actions show their reason.** When unsaved edits or prerequisites disable "Sign prescription", "Run safety check" or "Acknowledge", the reason is visible next to the button and linked with `aria-describedby`. The sign button references each reason list item by id, because a referenced list's `aria-label` would replace its text in the description.
- **Specimens:** `/dev/chart?view=mixed` and `/dev/prescribing?view=mixed` show blocking and advisory side by side, with inputs deliberately out of order to demonstrate the ordering.

### Phase 8c: shell polish and Figma alignment

- **Cursor.** A base rule in `globals.css` gives `cursor: pointer` to buttons, links with `href`, `summary`, `select`, ARIA buttons, menu items, tabs and options, checkbox and radio labels and inputs; `cursor: not-allowed` to `:disabled`, `[aria-disabled=true]` and labels around a disabled input. Text inputs keep the text cursor.
- **Initials.** One helper, `getInitials` (`src/lib/initials.ts`), for every avatar: grapheme-safe (`Intl.Segmenter`), drops honorifics ("Dr.", and others), suffixes and bracketed text, and takes the first and last name ("Dr. Avery North (synthetic)" → "AN").
- **Top bar order** (superseded in Phase 8d, see below): at 761px and up, search, Privacy pill, Today's queue, then (pushed right) sync status and the account menu. At 760px and below the search took its own row and the queue became a horizontally scrolling row under the sticky bar. The "Synthetic data" tag left the top bar; the synthetic-data banner remains.
- **Account menu** (`src/components/shell/user-menu.tsx`). The name, role, avatar and a chevron are the trigger (Phase 8e: only the avatar and chevron; the name and role are plain text) of a native `popover="auto"` menu (no library): "Privacy auto-hide" radio items and Sign out. WAI-ARIA menu button: `aria-haspopup="menu"`, `aria-expanded`, roving focus with arrow keys, Home and End (wrapping); ArrowDown on the trigger opens on the checked item and ArrowUp on the last; Escape closes and returns focus to the trigger; Tab and outside clicks close it. Space on a radio item selects and keeps the menu open; Enter or click selects and closes. Sign out also clears the Privacy state, the idle choice and the last-viewed patient. The name and role are visually hidden below `xl` (1180px) but stay in the accessible name.
- **Today's queue** (`src/features/patients/components/patient-queue.tsx`, `patient-queue-item.tsx`; logic in `src/features/patients/queue.ts`). Clinicians only. One query (`listMyQueue`) reads the care-team patients with their draft prescriptions and unresolved alerts under RLS; there is no per-patient query. Status per patient (revised in Phase 8d, see below): "Critical alert" if a draft has a blocking alert on its current version, "Warning" if it has an advisory alert on its current version without a decision, otherwise "No alerts". Allergies alone do not set a status. Ordered critical, warning, stable, then family and given name. Up to six chips plus "View all N patients". The current patient's chip has `aria-current="page"` on the chart and `"true"` on its deeper pages. "Back to patients" is gone; the list is reached through search, "View all" and the Chart rail item. Freshness: prescription actions revalidate the whole layout (`revalidatePath("/", "layout")`), so the queue re-renders after a mutation. If the query fails the queue shows "Queue unavailable" and the page still renders.
- **Sync status** (`src/components/shell/sync-status.tsx`). "Synced with Kestrel Health Network · N min ago" with a green dot; offline shows a red dot and the word "Offline". The time is the server render time, then the time of each client navigation, updated every minute without announcing it. Connection is `navigator.onLine` plus the `online` / `offline` events; only changes are announced ("Offline, changes are not syncing", "Back online") in the polite live region. Hidden below 1180px. The wording is fictional: nothing syncs anywhere.
- **Rail.** Chart, Schedule, E-Rx, Labs and Billing for clinicians (Audit for administrators). Chart and E-Rx open the current patient, else the last chart viewed in this tab (`kestrel.lastPatient` in `sessionStorage`), else the first queue patient, else the patient list. Schedule, Labs and Billing open `PlaceholderPage` ("Not part of this prototype"), with the shell landmarks, a heading and no patient data. The rail keeps its single avatar.
- **Allergy pill.** `Badge size="md"`: one line, at least 28px tall, 12px medium text, 12px / 4px padding, 6px gap, triangle icon; red when any allergy is severe, orange otherwise. The chart skeleton reserves the same pill box.
- **New icons:** `EyeIcon`, `RxIcon`, `FlaskIcon`, `BillingIcon`, drawn on the same 24px grid and 1.8 stroke as the rest. `AlertCircleIcon` was removed.
- **Contrast rows added** on `/dev/components` for the danger tokens at 12px, the Privacy pill, the account menu, queue chips and dots, and the sync line; see "Severity pairings" below.

### Phase 8d: top bar layout, Privacy button, queue statuses

- **Top bar grid** (`src/components/shell/app-shell.tsx`, utilities `grid-areas-topbar*` and `area-*` in `globals.css`). CSS grid areas, no JS measuring. Below `md`: search, then the right-aligned controls, then Today's queue, each on its own row. From `md` (761px): search (300px) and the controls on one row, the queue on its own full-width row below. From `queue-inline` (1440px), a queue with exactly one item (one chip, or "Queue unavailable") sits between the search and the controls instead (`grid-areas-topbar-inline`) and adds no row (Phase 8e: any item count, from its own measured breakpoint). Controls, left to right: sync status (from `xl`), the Privacy button, the account menu. The controls row is always `control-md` (40px) tall.
- **Queue wraps, never scrolls sideways.** Chips sit in `--queue-cols` fixed columns (2 below `md`, 3 from `md`, 5 from `xl`), each at most `--spacing-queue-chip` (11rem) wide, and wrap onto more lines. A long name truncates with an ellipsis; the accessible name keeps it whole. Still at most six chips plus "View all N".
- **Sticky offsets follow the bar's height, computed in CSS.** `data-queue-items` (chips plus "View all"; "Queue unavailable" counts as one) on the bar sets `--queue-items` through `:root:has(...)`; with the column count that gives the number of queue lines (`round(up, items / cols)`), and `--topbar-height` = the bar without the queue (`--spacing-topbar` 73px from `md`, `--spacing-topbar-stacked` 117px below, `--spacing-topbar-stacked-no-search` 65px for administrators below `md`; all derived from `control-md`, the bar padding and the hairline) plus the queue rows (32px per line, 8px between lines, 12px above). `--spacing-below-topbar` (`top-below-topbar`: chart context column, E-Rx review column, chart skeleton aside) and `scroll-padding-top` on `html` (`--topbar-height` + 16px) use it, so tracker jumps, anchors and sticky columns stop below the bar whatever its height. The section `scroll-mt-below-topbar*` classes and the fixed 120px offset are gone. A browser test asserts the rendered bar height equals `--topbar-height` for 1, 3 and 7 patients at 1440, 1024, 760 and 390px. The bar is rendered by the layout with the queue data, so loading skeletons do not draw it and nothing shifts on load.
- **Privacy button** (`privacy-controls.tsx`). A ghost button: no fill or border at rest, `surface-warm` fill on hover only, the normal focus ring. Off: `EyeIcon`, "Privacy", `ink-secondary`. On: `EyeOffIcon`, "Privacy on", `ok`. Same `aria-pressed`, shortcut, shared-cell width and icon-only rule below `lg` (820px) as before.
- **Queue statuses** (`queueStatus` in `src/features/patients/queue.ts`, unit-tested; one pure function so Phase 9 vitals can feed it). Only current drafts count. **Critical** (red): an unresolved blocking alert on the draft's current version. **Warning** (orange): an unresolved advisory alert on the current version without a decision, or a draft whose saved version has no safety check (`last_evaluated_version` differs from `version`). **Stable** (green): neither. A severe allergy alone changed nothing (reversed in Phase 8e: severe allergy critical, moderate warning). Still one query (`listMyQueue`), no per-patient queries. The chip's hidden status text now sits inline after the name, so the accessible name reads "Rowan Testcase, Critical alert".
- **Chip avatar colours (decorative).** Palette: teal, green, blue, defined once in `globals.css` as `--color-queue-avatar-1` / `-2` / `-3` (pointing at `avatar-teal`, `avatar-green` and the new `avatar-blue`, `#34618f`; Figma has no blue or info family). Swap a colour there; the `Avatar` tones `queue-1` to `queue-3` and `QUEUE_AVATAR_TONES` in `queue.ts` only name the slots. `queueAvatarTones` (pure, unit-tested) sorts the ids of **every patient the queue query returns, before the six-chip cap**, and gives index mod 3: so a colour ignores alert ordering, survives reloads, and does not change when a patient moves in or out of the visible six. A single patient is teal (slot 1). It changes only when the queue's membership changes (a patient with a lower id joining or leaving shifts the ones after it). `PatientQueueItem` receives it through `avatarTone`, its only avatar colour input; colour changes nothing in layout. **The colour carries no meaning:** status is only the dot and its text, the colour is never in an accessible name, and masked initials ("••") keep their colour. **Red is excluded** (the Figma `avatar-red` token stays unused): kestrel.mdc reserves red for severe and critical states, so a red avatar would read as an alert. Green is the same hue as `ok` / `status-stable`; it is acceptable only because the avatar is a large filled circle with initials, never a dot, and the stable dot always sits beside its "No alerts" text. White initials (11px, `text-caption`): teal 5.98:1, green 5.93:1, blue 6.46:1 (rows "Queue chip avatar slot N" on `/dev/components`). Specimen: `?queueOrder=rotated` on the `/dev` shell pages moves every status to the next patient, so the chip order changes while the colours stay.

Age and sex are one value, `formatAgeSex` (`src/lib/format.ts`): "62F" / "62M", or "62 unknown" for other values, masked together as one `PrivateText` ("Age and sex"), followed by " · DOB". With Privacy on it reads "•••••• · DOB ••••••"; nothing of the sex value shows. The `abbr` with the full sex as a tooltip is gone.
- **Rail labels.** Labelled rail items are 68px wide (`md:w-17`, was 52px) with 4px side padding and no wrapping, so "Schedule", the widest label, fits inside its item and the 76px rail. A test checks all five labels at 1440 and 761px.
- **Allergies card** on the chart: hairline outline in every tone (`danger-line` when any allergy is severe); the red icon, `danger-line` row dividers and `danger-ink` severe names stay. The 2px emphasis stays on the allergy-conflict banner and other blocking surfaces.

### Phase 8e: queue statuses with allergies, queue position, page width, account trigger, button states

- **Queue statuses include allergies** (reverses the Phase 8d "a severe allergy alone changes nothing"). `queueStatus` (still the one pure function, unit-tested) takes `{ drafts, allergies }`. **Critical**: an unresolved blocking alert on a current draft, **or an active severe allergy**. **Warning**: an unresolved advisory alert without a decision, a draft whose saved version has no safety check, **or an active moderate allergy**. **Stable**: none of those; mild allergies alone stay stable, inactive allergies are ignored. Still one query: `listMyQueue` embeds `allergies(severity)` filtered to `status = active` next to the drafts (RLS applies to both). Seeded baseline (no prescriptions): Rowan Testcase critical (active severe DEMO-ALPHA allergy; the mild one is inactive), Jordan Mockridge warning (active moderate DEMO-GAMMA), Elliot Samplewood, Morgan Fixture and Casey Placeholder stable. Drafts made later can raise a state, never lower the allergy floor.

## Line-height pairing (provisional)

Figma defines line heights by role, not per font size. Each size is paired with the closest role:

| Role (Figma) | Line height | Sizes using it |
| --- | --- | --- |
| `caption` | 16px | caption 11, label-sm 12, control-sm 12, code-sm 12 |
| `body` | 20px | label 13, body-sm 13, body 14, control-md 14, code-md 13, code-lg 14, button sm/md 14 |
| `heading-3` | 24px | body-lg 16, heading-sm 16, heading-md 18, data-sm 18, control-lg 16, button-lg 16 |
| `heading-2` | 28px | heading-lg 20 |
| `heading-1` | 32px | heading-xl 24, data-md 24 |
| `display` | 40px | display-md 32, display-lg 40, data-lg 32 |

Rules: text at or below 12px uses `caption`; 13–14px uses `body`; 16–18px uses `heading-3`; 20px uses `heading-2`; 24px uses `heading-1`; 32px and above uses `display`. `display-lg` therefore sets solid (40 on 40); multi-line samples are on `/dev/theme` for review.

`display-lg` 40/40 is accepted provisionally. `pnpm test:browser` checks the wrapped samples at 360, 760 and 1280px. At 40/40, Fraunces glyphs extend 4px past the last line box (IBM Plex Mono at `data-lg` 32/40 extends 1px); the lines do not collide, but do not put `display-lg` in a container with `overflow: hidden`, `truncate` or `line-clamp`, which would clip descenders. The test fails if any other sample overflows or these amounts grow.

### Privacy mode (Phase 8, in-place masking since Phase 8b)

**This is client-side shoulder-surfing protection only.** The patient data is already in the page (HTML, the React Server Component payload, memory); Privacy mode hides it from people looking at the screen. It is not access control, not a session timeout, and does not change authentication. Phase 8 hid the whole content area behind a "Content hidden" overlay, which behaved like a session lock; Phase 8b replaced it with field-by-field masking, like a password or card-number field. The page stays usable while masked.

- **`PrivateText` (`src/components/ui/private-text.tsx`).** Wraps one patient value. Shown: the value as text. Masked: a fixed mask (`••••••`) in the same text style, rendered as a button named "<field> hidden, press to reveal". While masked the value is not in the DOM text or the accessibility tree. `block` is for values that wrap over several lines (directions, label text). `revealable={false}` renders a plain `role="img"` mask named "<field> hidden", used where a button is not allowed or not useful: the patient name inside a list or chart link (a button cannot sit in a link), and avatar initials (mask `••`).
- **`PrivateField`.** Wraps an editable control (draft form fields, the acknowledgement note, the cancel reason). The control stays mounted, made `invisible`, `inert` and `aria-hidden`, and a mask button the same size covers it. So unsaved values, form submission and layout are unchanged. The value is still in the control's `value` (and, for a textarea, its initial text) in the DOM; only what is painted and exposed to assistive technology changes. A revealed control stays visible while focus is inside it. Inside `FormField` the control must be created in a client component, otherwise the label wiring cannot reach it.
- **Per-field reveal.** Click, Enter or Space on a mask shows only that field, for `PRIVACY_FIELD_REVEAL_MS` (10000, next to `PRIVACY_IDLE_MS` in `src/features/privacy/config.ts`), then it is masked again. Focus stays on the field across both swaps. The polite live region next to the Privacy button announces "<field> shown" and "<field> hidden".
- **Global toggle.** The Privacy button and Ctrl+. / ⌘+. mask or show every `PrivateText` and `PrivateField` on the page; focus stays where it is. One announcement per toggle ("Patient details hidden" / "Patient details shown"), never one per field. Turning Privacy off and on again re-masks any revealed field.
- **No layout shift.** Each value records its box while shown (and again just before masking). The mask takes that width (inline values, clipped) or height (block values) before paint, so nothing moves. Short identifiers (dates, MRN, quantity) do not wrap, because an inline value broken over two lines cannot be matched by a one-line mask. **Trade-offs:** the reserved width hints at the value's length; and a value first rendered while masked (after navigating with Privacy on) has no recorded box, so it uses the mask's own width and the line can move once when it is revealed.
- **Before hydration.** Server HTML contains the values. An unlayered rule in `globals.css` hides `[data-private-value]` (not revealed) while `<html data-privacy="on">`, so navigation, reloads and loading skeletons never paint a value; hydration then replaces them with masks.
- **Safety alerts stay visible.** Allergy conflicts, critical states and blocking or advisory alert text, including severity, allergen and drug names, are not masked, because hiding them could hide a safety signal. Only patient identifiers inside them are masked. The demo alert messages contain no patient identifiers today; the `/dev/privacy` specimen shows a critical alert with a masked patient name. The chart's alert banners name the medication (advisory: in the title; blocking: at the start of the body, since Phase 8f) and stay visible, while the same medication is masked in the prescriptions list.
- **Masked fields today:** patient name, initials, age and sex (one value since Phase 8d), date of birth and MRN on the patient list, chart and prescribing header; medications, doses, start dates and quantities; the prescription heading, drug class, directions, supply, instructions, cancel reason and acknowledgement notes; label preview text; every draft form field; the patient-list search summary (the query is usually a name or MRN). **Phase 9:** vital values and the reading time (the Critical / Warning / Stable label stays visible); sparkline trends (hidden, with no reveal); the HbA1c plot and its data table as one `PrivateRegion`; diagnosis codes, descriptions and dates; the hero's diagnosis tags as one region; encounter-note text (`PrivateField` while editing, `PrivateText` when read). Staff names on a diagnosis or a note stay visible. The audit page is not masked (out of scope).
- **Today's queue (Phase 8c).** Chip names and initials are masked; status dots stay. Each masked chip is named "Patient N of M, name hidden, <status>", so chips stay distinguishable.
- **Not masked:** the rail, the rest of the top bar, the synthetic data banner, headings and field labels, prescriber, version and status.
- **Search query.** The search field is a plain GET form. Turning Privacy on empties the field, including unsubmitted text, and removes `q` from the address bar with `history.replaceState`, which sends no request. Searching while Privacy is on strips the new `q` the same way. Turning Privacy off puts the last stripped `q` back if the URL has not changed since; unsubmitted text is not restored. The browser's own history and address-bar suggestions still hold the visited `?q=` URL, which the page cannot remove.
- **Toggle button (Privacy button, Phase 8d; a pill in 8c).** A ghost native button on the right of the top bar, after the sync status and immediately left of the account menu, with `aria-pressed`. Off: `EyeIcon` and "Privacy" in `ink-secondary`. On: `EyeOffIcon` and "Privacy on" in `ok`. No fill or border at rest; a `surface-warm` fill on hover only; the normal focus ring. The two labels share one grid cell, so the button keeps the width of the longer label and does not move when toggled; the accessible name follows the visible label. Icon-only below `lg` (820px). **Deviation:** the brief said icon-only at 760px and below; from 761px the top bar is a single row and the label does not fit beside the search until 820px, so the label appears from `lg`. Ctrl+. or ⌘+. toggles from anywhere, including text fields and, since Phase 8b, inside an open dialog (dialogs render the same masked components, so nothing has to close). **The Privacy button is the primary control; the shortcut is a convenience.** On macOS ⌘. is the system Cancel shortcut, and in Safari it stops loading the page, so it may not reach the page there (not tested). On Windows, Ctrl+. switches punctuation in the Microsoft Pinyin input method.
- **Auto-hide.** Chosen in the account menu ("Privacy auto-hide": 30 seconds, 1 minute, 2 minutes; `PRIVACY_IDLE_OPTIONS`), stored per tab in `sessionStorage` under `kestrel.privacy.idle` and read live by the idle timer. Default `PRIVACY_IDLE_MS` (60000); invalid stored values are ignored. Signing out clears it. Pointer, key, input, touch, wheel and scroll activity resets the timer, so typing never masks a field mid-keystroke. After the idle period Privacy turns on, or, if it is already on, every revealed field is masked again (one announcement). Open dialogs stay open; unsaved draft fields and a typed cancel reason are kept.
- **Reduced motion.** Masking and revealing have no transition or animation in any case.
- **Colour.** No red. Masks use the text colour of the value they replace; the form-field mask is `ink-strong` on `surface-warm` with the field border. Contrast rows on `/dev/components`: form-field mask 5.50:1, field edge 3.25:1 (UI), lightest inline use `ink-muted` on `surface` 5.24:1, link `accent` 5.89:1, alert `ink-strong` on `warning-subtle` 5.66:1.
- **State.** `sessionStorage` key `kestrel.privacy`, applied to `<html>` by an inline script in the root `<head>` before first paint. Per tab, never sent to the server, gone when the tab closes. The sign-in page turns it off; signing out removes the stored value, and the page stays masked until the browser leaves it.
- **Alternative not built: server-rendered placeholders.** A client `PrivateText` receives the value as a prop, so the value is in the RSC payload and in memory even while masked. A `privacy` cookie read in Server Components could render placeholders instead, so the data would not reach the browser at all while on. That makes every toggle and every reveal a server round trip, needs every page and skeleton to branch on the cookie, puts the cookie into each request and caching decision, and loses unsaved form state. It is the option to choose if the threat includes someone reading the DOM or the network, not just the screen.
- **Specimen:** `/dev/privacy` (404 outside development), with masked, revealed and fixed reference states, a critical alert, an encounter-note example, a dialog, `?skeleton=1` and `?delay=N`. Tests: `src/components/ui/private-text.test.tsx`, `src/features/privacy/*.test.ts(x)`, `tests/browser/privacy.spec.ts`, and the sign-out/sign-in case in `tests/e2e/auth.spec.ts`.

## Decision log

### Decision: red marks severity, not resolution (2026-10-22)

- **Before (Phase 5):** red was reserved for resolution actions and destructive confirms. Every detection state was orange, and blocking was told apart from advisory by a circle icon versus a triangle.
- **Now (Phase 8c, user decision):** red (error tokens) marks severe and critical states only; orange (warning tokens) marks moderate and warning states; green marks stable. The triangle alert icon is used everywhere and the circle variant is removed. Solid red is used only for the allergy-conflict banner and critical states; pills, dots and flags use the subtle or outlined error style. Blocking and advisory stay distinct by text label and border weight, never by colour alone. Red stays on the destructive "Cancel draft" confirm.
- **Phase 8e addition:** an active severe allergy makes a patient's queue dot critical; an active moderate allergy makes it warning.
- Details: "Severity colours" above and `.cursor/rules/kestrel.mdc`.

### Decision: abnormal vitals get a chart banner (2026-10-24)

- **Before (Phase 9, 23 Oct):** a critical vital showed on its tile (red, triangle, "Critical") and the queue dot only. A separate banner was left out as a second place for the same fact.
- **First build (user scope for Phase 9, 24 Oct):** the latest reading also raised a chart banner when any vital was warning or critical, so it sat with the other safety banners at the top of the chart.
- **Now (Phase 9b, user decision, 24 Oct):** the banner shows for **critical vitals only**. Warnings are tile-only on purpose: the tile already carries the warning state (orange, triangle, "Warning"), and the dashboard reference shows a warning blood pressure with no banner. When a reading has both, the banner lists the warning vitals below the critical ones. The tile stays the detailed view. Details: "Phase 9" above.

## Known issues

- **Dates follow UTC, not clinic time.**

- None open from Phase 5. The duplicate calendar icon is resolved above (native picker only).
- **Privacy masking can move wrapped values (Phase 8b trade-off, seen in Phase 8c).** An inline value that wraps over two lines is masked by a one-line mask. On the chart's prescriptions table at 390px the medication-name links wrap, so the table gets shorter by up to one line per row (55px on the blocking specimen) when Privacy turns on. The top bar, the queue and the hero do not move. A fix needs either fixed table column widths or a multi-line mask that keeps the auto-layout column widths; not done in 8c or 8d (accepted as a known limitation).
- **Known limitation: identical blocking banner titles (Phase 8f).** Two blocking drafts on one chart (on the same day, or both on earlier days) show the same title, "Allergy conflict on today's order" or "Allergy conflict on pending order", and differ only by the drug name in the body text and the "Review draft for <medication>" link name. Not fixed in Phase 9.
- **Known limitation: a renewal can leave two active medications (Phase 9).** Renew opens a new draft from a signed prescription and writes nothing until that draft is saved and signed. Signing adds another active medication and does not stop the earlier one.
- **Top bar height assumes one-line controls (Phase 8d).** `--topbar-height` is computed from tokens, not measured. If the controls or a chip ever wrapped (for example a much longer user name beside an inline queue), the bar would grow past the computed offset. Chips truncate and the inline queue column shrinks (`minmax(0, 1fr)`), so this does not happen with the current content; the height test would catch it on the specimens.
